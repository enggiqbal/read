 
# **A. MVP product description**

**Personal English Pronunciation Lab**

# **Read. Compare. Improve.**

A personal reading-practice application that compares original English text against speech-to-text transcripts to identify reading discrepancies, track recurring patterns, and generate targeted pronunciation exercises.

MVP scope

## **1. North Star**

**Help the user systematically improve American English pronunciation through measurable, repeatable reading practice.**

The application should move beyond one-time pronunciation feedback. Its long-term purpose is to identify persistent weaknesses across multiple reading sessions and turn those observations into targeted exercises.

The core learning loop:

**Read**

Original passage

**Transcribe**

iPhone Voice Memos

**Compare**

Word-level differences

**Improve**

Targeted exercises

Repeat the cycle and track progress over time.

## **2. Target user**

One user initially: the application owner.

The application is designed for someone who:

- Is learning American English pronunciation.
- Practices reading books, articles, and paragraphs aloud.
- Uses iPhone Voice Memos for recording and automatic transcription.
- Wants objective feedback rather than subjective impressions.
- Wants to identify recurring pronunciation difficulties.

## **3. Core functionality**

| Feature                 | Description                                   | Priority     |
| ----------------------- | --------------------------------------------- | ------------ |
| Original text input     | Paste text from a book or article             | Must have    |
| Transcript input        | Paste iPhone transcript                       | Must have    |
| Text comparison         | Identify substitutions, deletions, insertions | Must have    |
| Performance metrics     | Display three primary metrics                 | Must have    |
| Difference highlighting | Visually identify problematic words           | Must have    |
| Save session            | Persist all session data in JSON              | Must have    |
| Previous passages       | Search and load previous passages             | Must have    |
| Generate practice text  | Create passages targeting selected sounds     | Must have    |
| Historical analysis     | Find recurring patterns                       | Must have    |
| Progress chart          | Show session scores over time                 | Nice to have |

## **4. Three primary metrics**

Keep the main results interface limited to these:

1. **Transcription match percentage:** Percentage of original words correctly recognized, calculated using word error rate (WER).
2. **Words needing attention:** Number of substitutions, deletions, and insertions.
3. **Recurring patterns:** Most frequently observed error categories across sessions.

Important: These are speech-recognition-based indicators, not direct measurements of pronunciation accuracy.

## **5. Data collection strategy**

Persist more information than the interface displays.

Each session should capture:

- Session ID and timestamp.
- Original text.
- Recognized transcript.
- Word-level alignment.
- Substitutions, deletions, insertions.
- Word error rate and match percentage.
- AI-generated observations.
- Possible phonetic pattern tags.
- Passage source and generation settings.
- Whether the passage was original or generated.

This data should support future analysis of:

- Schwa production.
- Vowel recognition.
- Word stress.
- Unstressed syllables.
- Final consonants.
- Multisyllabic words.
- Commonly misrecognized words.

AI-generated phonetic classifications must be stored as hypotheses, not confirmed pronunciation errors.

## **6. Out of scope for MVP**

Do not implement these yet:

- Direct audio recording inside the application.
- Automatic audio uploads.
- Real-time pronunciation scoring.
- Acoustic vowel analysis.
- Praat integration.
- Forced alignment.
- User accounts and authentication.
- Cloud database.
- Complex analytics dashboards.

# **B. Developer instruction**

The following is the implementation specification. It is written as a standalone development brief suitable for a coding agent.

# Developer Specification: Personal English Pronunciation Lab

## 1. Project Overview

Build a lightweight, browser-based application called **Personal English Pronunciation Lab**.

The application helps a user improve American English pronunciation through repeated reading exercises.

The user provides two inputs:

1. Original text: A paragraph or passage copied from a book, article, or other source.
2. Recognized text: A transcript generated by the iPhone Voice Memos application.

The application compares both texts, identifies word-level differences, calculates performance metrics, and uses OpenAI to generate observations and targeted reading exercises.

The application must preserve historical sessions in a local JSON file.

## 2. North Star

Help the user systematically improve American English pronunciation through measurable, repeatable reading practice.

The core learning loop is:

Read → Transcribe → Compare → Identify Patterns → Practice → Repeat.

Prioritize longitudinal learning over one-time scoring.

## 3. Technical Architecture

Use the following stack:

- Frontend: React + TypeScript.
- Backend: Node.js + Express.
- Build tool: Vite.
- Styling: Tailwind CSS or a lightweight CSS solution.
- Database: Local JSON file.
- AI: OpenAI API through the backend.
- Charts: Lightweight charting library if needed.
- Package manager: npm.

Keep the application simple and modular.

Do not introduce unnecessary infrastructure, databases, authentication systems, or third-party services.

## 4. Deployment Environment

The application will run locally on the user's Mac.

Expose it to the internet using ngrok.

Expected architecture:

Browser → ngrok → Local Express server → OpenAI API

Requirements:

- Run the backend on a configurable port, default 3000.
- Configure Vite to serve the frontend through Express in production mode.
- Provide a development mode with separate frontend and backend processes.
- Configure ngrok to expose the Express server.
- Read the OpenAI API key from an environment variable.
- Never expose API keys to frontend code.
- Provide a `.env.example` file.
- Include clear npm commands for development and production.

Example commands:

`npm install`

`npm run dev`

`npm run build`

`npm start`

Document how to start ngrok and connect it to the application.

Note: ngrok provides a public tunnel to the locally running application. It is not a permanent hosting service. Protect access with an appropriate ngrok access policy if the application is reachable publicly.

## 5. Main Application Interface

Create a single-page application with three main sections.

### A. Reading Practice

Components:

- Original text textarea.
- Recognized transcript textarea.
- Analyze Reading button.
- Generate Targeted Practice button.
- Load Previous Passage button.

Provide a clean, responsive interface.

The user should be able to paste both texts without uploading files or recording audio inside the application.

### B. Analysis Results

After analysis, display exactly three primary metrics:

1. Transcription Match (%).
2. Words Needing Attention.
3. Recurring Error Patterns.

Below the metrics, display a detailed comparison.

Highlight:

- Correctly recognized words.
- Substituted words.
- Missing words.
- Extra words.

Use distinct, accessible visual treatments for each category.

Provide an optional details section for the complete word alignment and AI observations.

### C. Practice History

Allow the user to:

- View previous sessions.
- Search previous passages.
- Load a previous passage into the editor.
- View historical results.
- Reanalyze a passage if needed.

Keep history simple. Do not create a complicated dashboard.

## 6. Text Comparison Engine

Implement deterministic text comparison before calling OpenAI.

Use a word-level edit-distance alignment algorithm.

The comparison engine must identify:

- Correct matches.
- Substitutions.
- Deletions.
- Insertions.

Normalize text for comparison by:

- Standardizing whitespace.
- Handling punctuation consistently.
- Comparing words case-insensitively.
- Preserving original text for display.

Do not remove meaningful word distinctions.

Calculate:

Word Error Rate (WER):

WER = (Substitutions + Deletions + Insertions) / Number of words in original text.

Transcription Match (%) = max(0, 100 × (1 - WER)).

Keep the raw WER available in stored session data.

Do not treat punctuation differences as word errors.

Make the alignment deterministic so that the same two inputs always produce the same comparison.

## 7. OpenAI Analysis

Call OpenAI from the backend after deterministic comparison.

Send:

- Original text.
- Recognized transcript.
- Word-level differences.
- Relevant alignment information.

Ask the model to:

1. Identify meaningful word substitutions and omissions.
2. Suggest possible pronunciation-related explanations.
3. Identify possible phonetic categories:
   - Schwa /ə/.
   - Vowel quality.
   - Word stress.
   - Syllable reduction.
   - Final consonants.
   - Consonant clarity.
   - Multisyllabic word recognition.
   - Connected speech.
4. Identify potentially recurring patterns when historical data is provided.
5. Recommend a small number of targeted practice areas.

Important restrictions:

- Do not claim that a transcription mismatch proves incorrect pronunciation.
- Do not infer exact acoustic errors without audio analysis.
- Do not invent phonetic explanations when evidence is insufficient.
- Clearly distinguish observations from hypotheses.
- If a word has several plausible explanations, mention the uncertainty.
- Return structured JSON rather than free-form prose.

Use a strict response schema and validate the response before saving it.

Keep the OpenAI model configurable through an environment variable.

## 8. Targeted Practice Generation

Implement a Generate Targeted Practice feature.

The user can generate a new passage based on:

- A selected pronunciation focus.
- Historical error patterns.
- Difficulty level.
- Desired passage length.

Initial pronunciation categories:

- Schwa.
- Short and long vowels.
- Diphthongs.
- Word stress.
- Unstressed syllables.
- Final consonants.
- Multisyllabic words.
- Connected speech.

Provide three difficulty levels:

- Beginner.
- Intermediate.
- Advanced.

Provide three passage lengths:

- Approximately 75 words.
- Approximately 150 words.
- Approximately 250 words.

The generated result must contain:

1. Original reading passage.
2. Target pronunciation categories.
3. List of important target words.
4. Optional IPA for selected difficult words.

Save generated passages in the JSON database.

Do not automatically generate passages after every analysis. Generation must be initiated by the user.

## 9. JSON Database

Use a single local JSON file:

`data/database.json`

Create the file automatically if it does not exist.

Suggested structure:

{\
"version": 1,\
"passages": [],\
"sessions": []\
}

Passages should include:

- id
- title
- originalText
- source
- createdAt
- generated
- generationSettings
- targetPatterns

Sessions should include:

- id
- passageId
- createdAt
- originalText
- recognizedText
- metrics
- alignment
- errors
- aiAnalysis
- analysisVersion

Example metrics:

{\
"wordCount": 150,\
"substitutions": 3,\
"deletions": 2,\
"insertions": 1,\
"wer": 0.04,\
"transcriptionMatch": 96\
}

Store full original and recognized texts.

Store detailed word-level alignment.

Store AI-generated observations separately from deterministic comparison results.

Implement safe JSON persistence:

- Validate data before writing.
- Use atomic file writes (temporary file followed by rename).
- Prevent overlapping writes from corrupting the file.
- Create a backup before destructive changes.
- Never silently overwrite existing historical data.

Do not use a database server.

## 10. Historical Analysis

The application should retain enough information to analyze progress over time.

For the MVP, implement simple aggregations:

- Average transcription match.
- Most frequent substitutions.
- Most frequent error categories.
- Most frequently problematic words.
- Performance by passage.

Avoid presenting historical trends as definitive pronunciation improvements.

Keep the underlying data accessible for future analysis.

## 11. API Endpoints

Create a small REST API.

Suggested endpoints:

GET /api/passages\
POST /api/passages\
GET /api/passages/

GET /api/sessions\
POST /api/sessions\
GET /api/sessions/

POST /api/analyze\
POST /api/generate-practice

GET /api/analytics

Keep frontend and backend responsibilities separate.

Perform validation on all incoming requests.

Handle OpenAI failures gracefully and never save incomplete analyses as successful sessions.

## 12. UI/UX Requirements

Design principles:

- Minimal interface.
- Clean typography.
- Responsive layout.
- Desktop-first but mobile-compatible.
- Clear text highlighting.
- No unnecessary animations.
- No excessive cards or dashboard widgets.

The primary reading and comparison workflow should be accessible without navigating through multiple screens.

The application should feel like a personal study tool, not a commercial language-learning platform.

## 13. Security and Reliability

- Keep API keys server-side.
- Validate all user inputs.
- Limit request sizes.
- Protect JSON file operations.
- Do not expose arbitrary filesystem access.
- Add basic rate limiting to AI endpoints.
- Do not log API keys or unnecessarily log full reading content.
- Configure ngrok access protection before exposing the application publicly.

## 14. Development Process

Build incrementally.

Phase 1:

- Initialize the project.
- Set up React, TypeScript, Express, and Vite.
- Implement JSON persistence.
- Implement the reading interface.

Phase 2:

- Implement deterministic word alignment.
- Implement the three primary metrics.
- Implement highlighted comparison results.

Phase 3:

- Integrate OpenAI analysis.
- Add targeted practice generation.

Phase 4:

- Implement session history.
- Implement basic historical analytics.

Phase 5:

- Test persistence, error handling, and ngrok deployment.
- Write setup and usage documentation.

## 15. Acceptance Criteria

The application is complete when:

1. The user can paste original text.
2. The user can paste an iPhone transcript.
3. The user can analyze the comparison.
4. The application correctly identifies word substitutions, deletions, and insertions.
5. The three primary metrics are displayed.
6. Differences are visually highlighted.
7. OpenAI generates structured observations.
8. The user can generate targeted reading passages.
9. Sessions and passages persist in database.json.
10. The user can reload previous passages.
11. Historical data survives application restarts.
12. The application can be accessed through ngrok.
13. No API key is exposed in the browser.

## 16. Final Development Principle

Do not overengineer.

This is a single-user personal application.

Prioritize:

- Correct comparison.
- Reliable data storage.
- Useful feedback.
- Repeatable practice.
- Future extensibility.

Do not implement advanced acoustic pronunciation analysis in this MVP.

Build a working application first, with clean architecture that allows audio analysis and Praat integration to be added later.
